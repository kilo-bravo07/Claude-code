# ECR Monitor — GA4 Shopping + Checkout ECR Dashboard

An interactive replacement for a manually-maintained Google Sheet: a Shopping + Checkout Event Completion Rate
(ECR) dashboard driven by GA4 event data, with date/D-7/D-365 comparisons, automatic drop detection, city/platform/
device breakdowns, and a data-quality layer so a tracking gap is never mistaken for a real business drop.

## What this is

- **Frontend + backend**: Next.js 15 (App Router) + TypeScript, Tailwind CSS, Recharts. API routes under `app/api/*`
  serve JSON to client components — there is no separate backend process to run.
- **3 pages**: `/overview`, `/shopping`, `/checkout`, plus `/definitions` (formula/metric documentation).
- **Data provider abstraction**: `lib/data-providers/` — a `DataProvider` interface with a `MockDataProvider`
  (synthetic, clearly labeled "Demo Data") and a `Ga4DataProvider` (real GA4 Data API). The rest of the app never
  talks to GA4 directly.
- **Centralized metrics**: every formula (funnel %, ECR, pp change, severity) lives once in `lib/metrics.ts` /
  `lib/config.ts` / `lib/date-utils.ts` — no component recomputes a rate.

## Running it locally

```bash
npm install
npm run dev
```

Open `http://localhost:3000`. With no `.env` file, the app runs entirely on the **mock provider** — every page is
fully interactive against clearly-synthetic data (an amber "Demo Data" badge is shown in the filter bar). Nothing
about mock data is fabricated to look like Bakingo's actual numbers; it's generated by a seeded, documented formula
in `lib/data-providers/synthetic.ts` so it's reproducible and inspectable.

```bash
npm test          # runs the unit test suite (vitest) — 60 tests covering the calculation layer
npm run build      # production build + typecheck
```

## Connecting GA4

You said you only have **Viewer** access to the GA4 property — the setup below is written for that case. There are
two ways to authenticate; pick whichever your organization allows.

### Option A — your own Google account via OAuth (works with Viewer-only access)

The GA4 Data API respects whatever access *the authenticated identity* already has on the property. If your Google
account has Viewer access, authorizing the app as *you* is enough — no admin action needed.

1. In the [Google Cloud Console](https://console.cloud.google.com/), create or pick a project, then enable the
   **Google Analytics Data API** (APIs & Services → Library).
2. APIs & Services → Credentials → **Create Credentials → OAuth client ID** → Application type **Desktop app**.
   Download the client ID and client secret.
3. Get a refresh token for scope `https://www.googleapis.com/auth/analytics.readonly`, authorizing with the same
   Google account that has GA4 Viewer access. The quickest way is Google's
   [OAuth 2.0 Playground](https://developers.google.com/oauthplayground/):
   - Gear icon (top right) → check "Use your own OAuth credentials" → paste your client ID/secret.
   - Step 1: find "Google Analytics Data API v1" (or paste the scope above manually) → Authorize.
   - Sign in with your Viewer-access Google account.
   - Step 2: **Exchange authorization code for tokens** → copy the **Refresh token**.
4. Put all three values in `.env`:
   ```
   GA4_PROPERTY_ID=123456789
   GOOGLE_OAUTH_CLIENT_ID=...
   GOOGLE_OAUTH_CLIENT_SECRET=...
   GOOGLE_OAUTH_REFRESH_TOKEN=...
   ```

### Option B — service account (requires an org admin)

If someone with **Admin** access on the GA4 property is willing to add a service account as a Viewer
(Admin → Property Access Management → add the service account's email), this is simpler to operate long-term (no
refresh-token expiry to worry about):

1. Create a service account + JSON key in Google Cloud Console, enable the Google Analytics Data API on that project.
2. Have the property admin add the service account's email as a **Viewer** on the GA4 property.
3. Set:
   ```
   GA4_PROPERTY_ID=123456789
   GOOGLE_APPLICATION_CREDENTIALS=/absolute/path/to/service-account.json
   ```

Either option is enough — `lib/data-providers/index.ts` picks up GA4 automatically once `GA4_PROPERTY_ID` plus one
auth method is set. Set `DATA_PROVIDER=mock` to force demo data regardless (handy for screenshots), or
`DATA_PROVIDER=ga4` to force real data and fail loudly if credentials are missing, instead of silently falling back.

### GA4 event names — the part specific to your implementation

GA4's standard ecommerce events (`session_start`, `view_item`, `add_to_cart`, `begin_checkout`, `purchase`) are
correct out of the box. **The 4 intermediate checkout steps (Step 2–5) are not standard GA4 events** — they're
whatever custom events your site's GTM/gtag setup fires at each checkout step. Open your GA4 property → Admin →
Events (or check your GTM container) to find the exact event names, then set:

```
GA4_EVENT_CHECKOUT_STEP2=<your event name>
GA4_EVENT_CHECKOUT_STEP3=<your event name>
GA4_EVENT_CHECKOUT_STEP4=<your event name>
GA4_EVENT_CHECKOUT_STEP5=<your event name>
```

If you don't have 4 distinct events yet, wire up as many as you have — the funnel/table code handles it either way
(a missing event just reports 0 users for that stage, and the Data Quality panel will flag it as a possible
tracking gap rather than presenting it as a business drop).

## Environment variables (full list)

See `.env.example` for the complete, commented list. Summary:

| Variable | Required | Purpose |
|---|---|---|
| `DATA_PROVIDER` | no | Force `mock` or `ga4`; otherwise auto-detected |
| `GA4_PROPERTY_ID` | for GA4 | Numeric GA4 property ID |
| `GOOGLE_APPLICATION_CREDENTIALS` | one of this or the 3 OAuth vars | Service-account JSON path |
| `GOOGLE_OAUTH_CLIENT_ID` / `_SECRET` / `_REFRESH_TOKEN` | one of this or the service account | Your own OAuth credentials |
| `GA4_EVENT_*` | no (sensible defaults) | Override GA4 event names per funnel stage |
| `GA4_BRAND_DIMENSION` | no | Custom dimension name if you report multiple brands into one property |

## What's using mock data vs. real data today

- **Everything** runs on `MockDataProvider` until you set the GA4 env vars above — this is by design so the whole
  app (filters, comparisons, drop detection, breakdowns, charts) is fully demonstrable with zero configuration.
- Once GA4 is configured, **every page switches to `Ga4DataProvider` automatically** — no code changes, no separate
  "GA4 mode" build. The filter bar's badge changes from "Demo Data" (amber) to "GA4 Live" (green) so it's always
  obvious which one you're looking at.
- The synthetic data generator (`lib/data-providers/synthetic.ts`) intentionally injects a mild, deterministic
  "recent 14-day dip" concentrated in Android + Gurgaon so the drop-detection UI has something real to surface in
  demo mode — this is clearly a demo device, not a claim about Bakingo's actual performance.

## Validating your first real GA4 numbers

1. Set `DATA_PROVIDER=ga4` (so misconfiguration fails loudly instead of silently showing demo data) and the GA4 env
   vars above, then `npm run dev`.
2. Open `/overview`, set the date to a single recent day, comparison to "vs D-7".
3. Cross-check the **Shopping** numbers (View Item / ATC / Checkout / Purchase %, and the underlying user counts)
   against GA4's own UI: Explore → Funnel exploration with steps Session start → view_item → add_to_cart →
   begin_checkout → purchase, same date range, same filters. They should match (GA4 funnel exploration and this
   dashboard both use `activeUsers` scoped to each event, summed the same way).
4. Check the **Data quality** panel — if it flags `begin_checkout`/checkout-step coverage as critical, it almost
   certainly means the `GA4_EVENT_CHECKOUT_STEP*` env vars don't match your real event names yet; fix those before
   trusting the Checkout numbers.
5. Confirm City/Platform/Device breakdowns sum back to the same total as the unfiltered KPI cards (this is also
   covered by an automated test against the mock provider in `__tests__/mock-provider.test.ts` — the same
   sum-consistency invariant applies to the GA4 provider).

## Limitations from Viewer-only GA4 access

- You can **read** everything this dashboard needs (events, users, revenue, standard dimensions) with Viewer access
  — the Data API doesn't require Editor/Admin for reporting.
- You **cannot** create new GA4 custom dimensions or modify GA4 configuration yourself from this app, and the app
  never asks you to — it only reads whatever dimensions/events already exist.
- If you don't already have a "brand" custom dimension and there's only one brand, leave `GA4_BRAND_DIMENSION`
  unset; the brand filter will just show a single "Default" bucket rather than breaking.
- **Delivery City** (order destination) is not a GA4 concept and is not available from Viewer access to GA4 alone —
  see "City model" below.

## City model — GA4 City vs. Delivery City

GA4 only ever gives you **GA4 City**: a geo-IP-derived city for the visitor/session, not the delivery destination.
This dashboard labels it explicitly as "GA4 City" everywhere (filters, breakdown tables) rather than implying it's
the shipping address. The reporting data model (`lib/types.ts` → `ReportingRow`) has a separate, currently-null
`deliveryCity` field reserved for a future non-GA4 order-data source (e.g. your order database or a warehouse
export) — wiring that up later only means implementing a new `DataProvider` (or extending the existing one) that
also populates `deliveryCity`; no restructuring of the dashboard is needed.

## Architecture reference

```
lib/
  types.ts              normalized reporting row + shared types
  config.ts             ALL tunable thresholds (severity pp cutoffs, cache TTL, drop-table row count, etc.)
  date-utils.ts          D-7 / D-365 / range comparison-period math
  metrics.ts             the only place funnel %, ECR, pp/relative change, severity are computed
  data-quality.ts        modular data-quality checks (add a new check by extending the CHECKS array)
  view-model.ts           wires current/D-7/D-365 counts into per-card view models
  cache.ts                in-memory TTL cache so repeated filter changes don't re-hit GA4
  data-providers/
    types.ts              the DataProvider interface — the one seam to GA4
    mock-provider.ts       synthetic demo data
    ga4-provider.ts        real GA4 Data API calls
    ga4-config.ts          all GA4 event/dimension names, read from env
    synthetic.ts           deterministic mock-data generator
    index.ts               provider factory (env-driven selection)
app/
  api/*/route.ts          thin route handlers: parse query -> call provider (cached) -> JSON
  overview/, shopping/, checkout/, definitions/   the 4 pages
components/               presentational + data-fetching UI components
hooks/                    useDashboardFilters (URL-backed global filters), useApiData, etc.
__tests__/                vitest unit tests for the calculation layer
```

### Adding a new funnel step

1. Add the raw count field to `ReportingRow`/`FunnelCounts` in `lib/types.ts`.
2. Add the stage to `computeShoppingFunnel` or `computeCheckoutFunnel` in `lib/metrics.ts` (and to
   `SHOPPING_FUNNEL_STAGES`/`CHECKOUT_FUNNEL_STAGES` in `lib/config.ts`).
3. Populate it in both providers: `synthetic.ts`/`mock-provider.ts` (demo) and `ga4-provider.ts` (add to
   `FUNNEL_EVENTS` + a `GA4_EVENT_*` env var in `ga4-config.ts`).
4. No UI changes needed — funnel tables, cards, and diagrams all render from `computeShoppingFunnel`/
   `computeCheckoutFunnel`'s output.

### Changing drop-severity thresholds

Edit `SEVERITY_THRESHOLDS` in `lib/config.ts`. Every severity badge, cell highlight, and "Where did ECR drop?"
ranking in the app reads from this one object.

## Known limitations / what's left

- The GA4 provider (`lib/data-providers/ga4-provider.ts`) is implemented against the documented Google Analytics
  Data API (`runReport`, event-scoped `activeUsers`/`purchaseRevenue`/`transactions`) but has not been exercised
  against a live GA4 property in this environment (no GA4 credentials were available here) — validate it against
  your property using the steps above before relying on it for daily reporting.
- `npm audit` reports a handful of moderate-severity advisories in transitive dependencies of
  `@google-analytics/data` (an old `uuid` version pulled in via `google-gax`/`gaxios`) and in Next.js's own bundled
  `postcss` (fixed only in the Next 16 line as of this writing). None are exploitable through this app's own code
  paths (no user-controlled input reaches those packages), but re-run `npm audit` periodically and upgrade when
  fixed versions land.
- "Brand" is a single-value filter today (`Default`) unless you configure `GA4_BRAND_DIMENSION` — there's no
  built-in multi-brand demo data beyond the two synthetic brands in mock mode.
